# Studio → Website ingest checksum contract

## Purpose

The Website must verify the integrity checksum generated by Baribudos Studio before validating or persisting a publication envelope. A syntactically valid 64-character SHA-256 value is not sufficient.

## Version 1 algorithm

Studio currently computes:

```python
canonical = json.dumps(
    envelope_without_checksum,
    ensure_ascii=False,
    sort_keys=True,
).encode("utf-8")
checksum = hashlib.sha256(canonical).hexdigest()
```

The Website verifier follows the same Python JSON serialization contract:

- Remove only the top-level `checksum` property before hashing.
- Sort object keys by Unicode code point at every nesting level.
- Preserve array order.
- Preserve Unicode characters (UTF-8; do not ASCII-escape them).
- Use Python's default JSON separators: comma + space and colon + space.
- Preserve numeric tokens from the raw request body. This matters for values such as `1.0`, which JavaScript's `JSON.parse` would otherwise normalize to `1`.
- Compare the computed SHA-256 digest with the supplied hexadecimal checksum using a constant-time byte comparison.

The route verifies the raw body before Zod parsing because schema defaults and normalization must not alter the bytes/values covered by the Studio digest.

## Shared cross-language fixture

`tests/fixtures/website-ingest-v1-checksum.json` is shared byte-for-byte with the Studio repository at `tests/fixtures/website-ingest-v1-checksum.json`.

Its digest was generated by Python's `hashlib.sha256(json.dumps(..., ensure_ascii=False, sort_keys=True).encode("utf-8"))`. It includes Portuguese Unicode, an emoji, decimal values and a `1.0` float token.

- Website Node tests verify acceptance and rejection after payload/checksum tampering.
- Studio Python test recomputes the fixture digest using the production algorithm.

## Compatibility and rollout

This is verification of the existing `website_ingest_v1` checksum contract; it does not change the Studio envelope or checksum generation. Invalid/missing/malformed digests are rejected before database writes. The API key remains the authentication mechanism; SHA-256 is an integrity check, not a signature or replacement for authentication.
